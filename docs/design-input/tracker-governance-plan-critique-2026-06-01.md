## 1. Top 3 under-specified seams

1. **Header summary vs. governance-doc boundary (the DRY seam; decision 3 / Items 1-3).** The doc owns the full write-gate (5 positive conditions plus 6 negative cases) and the schema. The header carries "a short write-gate summary + a pointer." `CLAUDE.md` links only. The middle tier is undefined: does the header restate the 5-and-6-part gate (duplication the plan elsewhere forbids), or a one-line "accepted, concrete, unresolved, future, unowned, see the governance doc" (which forces a click before every write)? An implementer will guess, and the guess decides whether the gate is applied at the point of use. Pin the exact header payload in Item 1. My recommendation: one-sentence gate plus the negative-case list inline (the negatives are what stop bad writes and are cheap to carry), full rationale in the doc.
2. **Archive-file format (Item 2 / decision 4).** "Documented format ... (disposition, rationale, date)" never says whether an archived entry keeps the full detail schema or collapses into a stub. That choice has two opposing pulls. A rejected entry has value only if it stays recognizable enough that a later agent avoids re-proposing the same settled non-goal. A cheap active read pushes the other way and wants a small archive. Entry order inside the file is open as well. The Open Question about a status split is really this seam. My recommended shape for each archived record is short. It keeps the original ID and Problem statement. A disposition and a dated one-line rationale sit alongside. New rows append in ID order.
3. **"Upgraded to satisfy the detail schema" for kept entries (Item 4).** TD-008, TD-009, and TD-010 already carry dates and rich context. TD-007 does not: it has no explicit `Discovered`, `Why deferred`, `Trigger`, or `Done when`. Backfilling `Discovered: date + originating context` for an entry whose origin was never recorded forces invention. Say so explicitly: use "Discovered: pre-v0 baseline (origin not recorded)" rather than a fabricated date, and scope Item 4's upgrade work mainly to TD-007 (the others largely conform already).

## 2. Specificity balance (plan vs. export)

- **Over-prescribed.** The schema is presented as six fields with "detail is welcomed, not rationed." The export's framing was lost: "enough to prevent dead-weight entries without creating a heavyweight issue-template culture." The claude-toolkit model it cites has entries running about 40 lines each, so mandating six fields on every future entry risks recreating the friction the gate is meant to remove. Restore the export's caveat: the fields mark the ceiling for what is useful, not a required template. Thin-but-clear entries are allowed. (Minor fidelity note: the cited model actually leans on `Trigger to revisit` plus `Suggested approach`; `Done when` is the plan's addition, not claude-toolkit's. That is fine, but do not claim it is "the field set the user already admires.")
- **Dropped framing worth recovering.** The export had a consolidated Risks and migration section (its §6); the plan has none, and risks are scattered into done-when bullets. The most important dropped risk is the export's own "policy becomes too verbose and agents skip it; keep the header concise; avoid a separate design doc for v1," which is the direct counter-argument to decision 3 and belongs on the record even though the user overrode it. The verification scenario table was retained (Item 8), so that one was not lost.

## 3. Contradictions and missing dependencies

- **TD-007 is reshaped twice (Item 4, then Item 5), which risks rework.** Item 4 upgrades TD-007 to the full schema. Item 5 may then decide `preset-architecture.md` owns the React-preset summary and the tracker only links to it, partially undoing Item 4. Resolve Item 5's TD-007 ownership before Item 4 upgrades that entry.
- **Active-header forward-reference.** Item 2 has the header assert "gaps resolve to the archive," but the gaps do not exist until Item 4 migrates entries. This is not a contradiction (Item 2 creates the archive file), but the header states something only Item 4 makes true, which is worth a note.
- **Item 6 (and Item 7) are over-blocked.** Item 6 declares a dependency on Items 1-5, yet the global rewrite distills the policy model (write-gate, schema, lifecycle = Items 1-2), not the local entry migration (4) or prose repointing (5). Blocking the global edit on 4-5 serializes the session needlessly and pushes the "harden globals this session" commitment to the very end, where it is most likely to be rushed. Item 6 should depend on Items 1-2 only.
- Dependencies that are correct: Item 2 on Item 1 (archive format needs the schema), and Items 3 and 4 both on Items 1-2. No edges are missing there.

## 4. Over-planning: the honest call

The plan sits at the ceiling of defensible structure, but it is not beads-style ceremony. What the user rejected in beads was operational: a daemon, a CLI, JSONL, hash IDs, a dependency graph. This plan adds none of that. It adds documentation surface instead. The new shape has two tracker files (active and archive) governed by one design doc, with a router link from `CLAUDE.md`. Two honest points. First, the archive file is not empty scaffolding, because Item 4 moves 5 entries into it on day one. Second, the governance design doc for a 4-entry backlog is the part most exposed to the critique, since the export's second opinion explicitly recommended against creating it for v1. The user overrode that, which is legitimate, but it means the plan's real failure mode is DRY drift across the four surfaces (exactly seam #1), not runtime overhead. To keep that risk down inside the decisions: keep the doc tight and make the header a near-pure pointer. Folding the Item 8 scenario table into the governance doc as worked examples would also give the doc a second job beyond restating prose the header already carries.
