## Vision (one paragraph)

`introspection` is a governed, typed, agent-maintained record substrate: structured markdown records with per-type lifecycles, a mechanically enforced shape, portfolio-wide, optionally search-indexed. A tech-debt tracker is record type #1. Mistakes / desires / learnings are the introspection record-type family. The differentiator is the **conversion lifecycle**: a record is not "done" when written, only when it has changed the environment (a mistake becomes a check, a desire becomes a built tool, a learning becomes a promoted doc), and then it is archived. A **second core capability**: introspection also maintains frontmatter-tag hygiene across the repo's opted-in markdown corpus (design-docs, references, and other docs) against a per-repo controlled vocabulary — owning those docs' *tags*, never their content or lifecycle — so the whole repo becomes a consistently tagged GNO corpus and `prime`/hooks can inject precisely scoped context. UI/renderer, GNO retrieval, and a future ticket->agent automation are all *consumers* of the substrate, never part of it.

## DECIDED (apply as-is)

- **New separate repo, name `introspection`** (name chosen for vibes; keep the engine conceptually separable underneath so it is not welded to one record type).
- **First customer = `backpressure`**: migrate its tech-debt tracker as record type #1.
- **Language: Effect / TypeScript.**
- **Source of truth = plain markdown + frontmatter.** The core owns and serves its own structured data/export. GNO is a *parallel* retrieval consumer, never the data source. The renderer/UI consumes the core's export, not GNO. Nothing in the core depends on GNO.
- **Record-type-agnostic engine via a plugin/adapter contract.** Each record type is a plugin declaring its schema + lifecycle states + allowed transitions + how it resolves. Design the contract *aware introspection is coming* (do not hardcode open/closed), but build and validate tech-debt first; introspection as the second plugin is the validation that the contract is expressive enough.
- **ID model `(repo, key, number)`.** The project key lives in the repo's own committed config. Cross-repo uniqueness is an aggregation/display concern: the aggregator namespaces on collision. No central registry is required for correctness (optional convenience only). Multi-user / work-repo safe by construction; do not bake single-owner assumptions into IDs.
- **Mechanics universal; judgment per-adopter.** The tool (schema, lifecycle, IDs, lint, export, surfacing) is the same for everyone. Judgment (write-gate criteria, what counts as a real mistake, what to prune) is per-adopter prose the tool *surfaces but never contains*. The tool carries its own minimal config plus an optional pointer to wherever the adopter keeps its policy. It does NOT impose the adopting repo's doc taxonomy (no standardizing design-docs/ADRs across repos).
- **Tag hygiene across the opted-in markdown corpus (second core capability).** Beyond record lifecycles, introspection helps agents maintain frontmatter tags on all opted-in md (design-docs/references/etc.) so the full repo is a first-class GNO corpus. The split: the agent/model *chooses* tags and *proposes* vocabulary additions (judgment); the CLI holds a **per-repo controlled vocabulary** (a config, like Vale `accept.txt`/doc-garden), validates tags against it, detects missing/invalid/stale tags, `--fix`es deterministic parts, and surfaces what needs attention (mechanics). It owns the docs' *tags*, never their content/structure/lifecycle. The corpus is **opt-in by config globs** (do not blanket-tag every md). Embeddings give baseline retrieval untagged on day one; tags are the precision/filtering + current-vs-historical-scoping enhancement, so this is the increment *after* the record layer and is what unlocks precise `prime`/hook injection. Maintenance is **nudge-at-boundaries** (lint in `check`/CI, a session-start/`prime` tag-debt summary, optional pre-commit) with batched agent fixes — *not* a per-md-edit hook (overkill + churn).
- **Operating model (who runs what).** Agents run the CLI (the machine interface); the human does not operate it. The human is the judgment authority for the few taste-shaping decisions (approve a novel vocab term, decide a prune). In v1 (no UI) the agent surfaces those in the conversation and the human answers inline; the UI later makes the same review async/batched. Review intensity is a **per-repo dial** the adopter sets — from strict (approve each new vocab term) to loose (agents provisionally self-manage, the human or a dedicated agent prunes occasionally) — and the tool always surfaces accumulating debt (pending vocab, tag debt, conversion debt) so the human is never blind. Minimize and batch judgment; never eliminate it.
- **`prime` (a.k.a. `context`) CLI command is the universal primitive**: it teaches CLI usage and surfaces the relevant records. Harness hooks are optional sugar over it. Works on Codex and Claude. Codex supports hooks, but per-repo hook config is uncertain, so the CLI keys off cwd/repo to scope per-repo behaviour regardless of how it is invoked. A Claude plugin/hook is the nice auto-wiring; an `AGENTS.md`/`CLAUDE.md` one-liner ("run `introspection prime`") is the universal floor. All intelligence lives in the CLI; harness wiring is a thin shim.
- **Conversion lifecycle is the core principle and the anti-bloat mechanism.** A mistake/desire/learning leaves the active set once converted/promoted. `prime` surfaces only the active (unconverted/unpromoted) and relevance-scoped set, and it surfaces the conversion-debt count so rot is visible. Prefer the strongest, lowest-ongoing-context conversion target: an enforced check/hook beats a doc, which beats a global rule. (Per MP's escalation ladder in `~/.claude/CLAUDE.md` "## Meta": verbal -> memory -> CLAUDE.md/doc -> enforced hook/check. In MP's repos the repo `CLAUDE.md` is a thin router and global is reserved for universal rules, so the middle rung is really "a doc," not a repo-CLAUDE.md line.)
- **Factory seam: design for it, do not build it.** Status is a machine-readable enum in frontmatter; transitions go through the CLI (one observable path). That is the only seam a future ticket->agent — or, for MP's non-one-shot flow, ticket->deep-plan-run — automation needs. Build none of that automation in v1.
- **Global instruction: replace, do not delete** (`claude-toolkit/GLOBAL_CLAUDE.md` / `GLOBAL_AGENTS.md:4-5`). Keep the invariant (do not bury an accepted, concrete, unresolved gap found during real work; if the repo defines a tracking system, follow it; otherwise raise it to the user). Drop the reflexive tracker-first persistence of brainstorms, rejected ideas, and same-session work.
- **v1 scope and order (one plan, explicit gate):** engine + tech-debt record type -> dogfood in `backpressure` (the gate) -> introspection record types (mistakes/desires/learnings) -> full-corpus tag hygiene (the increment that unlocks precise injection). Headless core; everything else is a consumer. Lean vertical slice before breadth. Agent throughput is not the constraint; validating the plugin contract on the simple type before the hard one is.
- **Architecture: real ports, not paper seams — build the scalable shape in v1.** Code is cheap and this substrate is meant to live years, so build the extension points as actual interfaces with contract tests, not deferred "later" seams. Ports/adapters split: real extension points (RecordType registry, retrieval/export adapters, `prime` selector, output presenters), internal seams for testability (RecordStore, ID allocator, clock, config loader), and intentionally-fixed invariants (markdown source of truth, vocabulary integrity, lifecycle enforcement, schema validation, judgment-stays-in-adopter-prose). Each port ships **≥1 real impl + 1 trivial proving impl** (retrieval = GNO + a JSON/`none` fallback) so swappability is demonstrated, not asserted. Static compiled registry; **no dynamic/runtime plugin loading** in v1. GNO is swappable behind a neutral retrieval/export *projection*, and provider-specific IDs never become canonical. The only deferral is concrete adapters with no consumer yet (tracker TD-008).
- **No off-the-shelf tool fits the core; do not adopt one.** Adjacent categories are the wrong shape: agent-memory (Mem0/Zep/Letta/LangGraph) is app/user memory, not repo-owned typed lifecycle records; markdown task tools fail source-of-truth or scope (**Beads is ruled out — JSONL, not markdown**); PKM (Obsidian/Dataview/Dendron) relies on human discipline and has no agent-operated conversion lifecycle; retrieval engines (GNO/Sourcegraph/Vespa) are consumers, not the substrate, so **do not build retrieval — use GNO**. The defensible novelty is the combination, and specifically the **conversion-lifecycle-as-anti-bloat** gate; v1 must prove that, not just a nicer tracker.
- **The deep plan includes a prior-art / alternatives research phase.** Before freezing the architecture, research adjacent systems to borrow proven *shapes* (temporal-memory modeling à la Zep, MemGPT memory hierarchy, structured issue-form intake, lifecycle/state-machine patterns) to inform shape, not to find a tool to adopt. The oracle's first pass is in `investigations/oracle-preplan-critique-2026-06-01.md`; the plan deepens it. (Candidate to promote into taste-distillery canon: "scan prior art for shape before settling a new system's architecture" — cheap with agents, good hygiene.)
- **Config/data formats chosen by slot, not by authorship (per taste-distillery ADR-002 `decisions/002-config-and-data-formats.md`).** The deciding axis is which consumer reads the file, not whether a human typed it (both YAML and TOML are hand-authorable). **YAML** for markdown frontmatter (the ecosystem default GNO/editors/parsers expect; TOML frontmatter would hurt interop). **TOML** for standalone hand-authored config such as the repo config (safer than YAML for mixed human+agent edits: explicit types, comments, no significant-whitespace or Norway-problem footguns; Taplo + JSON-Schema validation). **JSON** for generated/disposable artifacts (the GNO export projection, prime cache). **JSON Schema** for validation rules. The vocabulary's shape is left to the plan: a standalone `vocabulary.toml` (TOML) vs each term as its own record (YAML frontmatter like any record).

- GNO adoption specifics (collections, cross-repo indexing). Retrieval layer; likely roadmap, not v1.
- Multi-user / productization / permissions layer beyond a personal portfolio. Roadmap.

- The exact global-instruction rewrite wording.
- Repo/name confirmation (`introspection` flagship vs an engine-neutral name with introspection as a module).
- **Reconcile with backpressure's in-flight plan** `/Users/mp/Projects/personal/introspection/docs/design-input/tracker-governance-2026-06-01.md`: it is likely superseded by "backpressure adopts introspection" rather than hand-rolling its own governance. Decide explicitly what happens to that plan and its design-critique doc.
- The judgment/policy surface the tool carries (which config fields, where the policy pointer lives). This is the topic we kept circling; resolve it concretely in the plan rather than in the abstract. The per-repo tag vocabulary is one concrete piece of this surface.
- **Vocabulary governance (key risk).** The controlled tag vocabulary itself sprawls (synonym creep) if agents append freely. Growing it must be gated — propose + dedupe-against-existing + periodic review, never silent append — or it becomes an `accept.txt` graveyard one level up. Direction: the vocab has **referential integrity** with the corpus, so every mutation (rename/merge/delete) is a **cascading migration the tool performs** (rename propagates to all docs; delete only if unused or via merge) — CRUD is safe only through these ops, never raw list edits. Approval friction is minimized by **mechanical auto-dedupe** (reject near-synonyms by string/embedding similarity, no human), **provisional-accept** (never block the agent), and **batch review** of pending terms — ideally via the web UI with the CLI opening a deeplink, not per-tag inline. v1 does this with CLI `vocab` commands; the UI is a roadmap consumer.
- **Tag stability / anti-churn.** Re-tag only on material content change; avoid different models re-tagging the same doc across sessions. The controlled vocab + validation stabilizes it. A new vocab term does **not** force mass re-tagging of existing docs — it is available going forward and applied as docs are touched, with an optional explicit backfill pass; a doc's tags are revisited when its own content/state materially changes.
- **Tag-maintenance trigger and UX:** which checkpoints surface tag debt (lint vs `prime` summary vs pre-commit) and how the agent batch-fixes.
